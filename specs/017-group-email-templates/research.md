# Research: Group Email Templates and Check-In UX

## Decision 1: Persist defaults during group query reads when template fields are missing

- Decision: During group read/query flows used by the website, detect missing or empty `publishEmailMessage` and `attendanceEmailMessage`, then persist defaults via a targeted update so subsequent fetches return editable values.
- Rationale: This directly satisfies the requirement to insert defaults when values are absent and ensures frontend forms always receive editable content.
- Alternatives considered:
  - Frontend-only fallback values without persistence. Rejected because values would not be saved unless the user manually submits.
  - Migration-only backfill job. Rejected because legacy and newly created incomplete records can still appear over time.

## Decision 2: Store template fields as HTML-compatible rich text content

- Decision: Keep template fields as HTML-compatible strings generated by rich text editors (TipTap), and render them as template source for email composition.
- Rationale: Requirement explicitly calls for HTML compatibility and rich text authoring in group and meeting forms.
- Alternatives considered:
  - Plain text only with newline formatting. Rejected because it cannot support required rich text formatting.
  - Markdown source storage. Rejected due to conversion overhead and potential mismatch with existing editor stack.

## Decision 3: Use explicit seeded defaults for group templates

- Decision: Seed group template defaults with:
  - `attendanceEmailMessage`: `TODO: add template here`
  - `publishEmailMessage`: exact baseline template containing placeholders and `[checkinButton]` token.
- Rationale: Matches requested template behavior and provides deterministic first-load content.
- Alternatives considered:
  - Generic short placeholder text. Rejected because it does not satisfy the requested publish template text.
  - Empty-string defaults. Rejected because it fails auto-populate expectations.

## Decision 4: Parse placeholders at send time in publish email renderer

- Decision: Implement placeholder replacement at email send/build time using meeting data values:
  - `[meetingName]`
  - `[meetingDate]`
  - `[meetingTime]`
  - `[meetingAddress]`
  - `[dateOfNotification]`
  - `[checkinButton]`
- Rationale: Ensures latest meeting details are reflected and preserves editable template source in storage.
- Alternatives considered:
  - Parse and store rendered content during meeting edit. Rejected because it becomes stale when meeting values change.
  - Only parse on publish action and save result. Rejected because it reduces repeatability and testability of template rendering.

## Decision 5: Render check-in CTA as themed button after main body content

- Decision: Resolve `[checkinButton]` to a large themed button in HTML email output linking to the specific meeting URL; keep readable equivalent link text in plain text body.
- Rationale: Meets requirement for a prominent check-in action after body text while preserving accessibility and text-mode compatibility.
- Alternatives considered:
  - Inline text link only. Rejected due to reduced visibility and failure to satisfy “big themed button.”
  - Hard-coded button appended regardless of placeholder token. Rejected because template should remain author-controlled.

## Decision 6: Mirror meeting card check-in behavior on meeting details page

- Decision: Add check-in controls to meeting details page using the same attendance-state actions and mutation semantics as meeting card flow.
- Rationale: Consistent mental model and lower implementation risk through behavior reuse.
- Alternatives considered:
  - New details-only check-in workflow. Rejected because it creates UX divergence.
  - Link out to existing card only. Rejected because requirement explicitly asks for check-in UI on details page.

## Publish Template Baseline

```text
Good morning my author friends!

This is a reminder about our [meetingName] on [meetingDate] at [meetingTime] at [meetingAddress].

Please RSVP if you plan to attend AND if you have pages to read.
(Even if you're not reading, we need an accurate headcount to know how many copies to bring)

[checkinButton]

<b>*To ensure your reservation, please respond to this email no later than 5pm [dateOfNotification]. </b>

If we have more than six readers, this will allow us to reserve a second room in advance.

Warmly,

Administrator Name here
```
